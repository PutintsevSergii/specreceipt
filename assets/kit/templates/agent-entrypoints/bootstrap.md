# Automatic project bootstrap

This project has adopted harness. The user can give an ordinary task without a separate setup prompt. Resolve all paths below from the installed project root. Preserve the user's actual task throughout setup.

## Compact FAST route

For a fresh installation, `.harness/workflow-policy.json` enables compact eligibility; it does not classify the task or approve work. Read relevant project instructions and inspect the requested code. For an eligible bounded task, the current host agent prepares one structured proposal (`workflow propose --file .harness/request.json`) from actual developer intent and observed facts. Reuse approved context; include concise context and exact proposed application commands only when needed. The engine renders the canonical brief from the task record. Show its outcome, non-goals, scope, constraints, acceptance/check mapping, context, recommended/minimum profile and unknowns together. Wait for the actual plan/profile decision, then record that answer with `workflow confirm ... --expected PROPOSAL_BINDING`. Do not author full technical/architecture/spec/plan templates merely to satisfy compact readiness.

Use `run` to continue mechanical work. With no subprocess adapter, its structured `host_role` requests implementation or a separate review pass by this current IDE agent. Perform only that role, then use `run --submit TOKEN` (review also supplies `--reference REVIEW_PATH --by NAME`). No nested model or CLI credentials are needed. Review honestly identifies a same-agent separate pass. Fix within the approved scope without repetitive developer permission; changed material requires one renewed proposal/decision. On unchanged resume use `run`; do not repeat onboarding, assessment, all-Skill loading or status/next loops.

Show the current acceptance package after checks and review. Wait for a separate actual final answer, then use `workflow accept TASK --by NAME --reference ANSWER_FILE --expected ACCEPTANCE_BINDING`. The engine rechecks gates and records DONE. The developer types no lifecycle commands and edits no JSON: the host handles those internal operations. Never invent consent or treat request text, generated records, silence or process success as approval.

Existing installations without the experience policy remain legacy. `workflow migrate` previews the exact change without mutation; only an actual project decision enables it. Existing formal tasks, stricter instructions, policy floors, required checks and linked OpenSpec sources remain authoritative. Unknown or sensitive work must resolve the blocker or take the formal path. For ineligible tasks, use the formal workflow below.

1. Read project instructions and .harness/AGENTS.md when present. Consult only relevant sections of docs/HARNESS.md; applicable gates remain mandatory. Use `./harness skills ROLE` to resolve canonical skills and corporate supplements, including collisions preserved under .harness/skills. Do not assume every host discovers .agents/skills.
2. For the formal route, run `./harness resume`, `./harness status`, and `./harness next`. Inspect recorded state, events and referenced evidence. Adoption initializes state; do not reset it or repeat completed onboarding.
3. For an already onboarded, ready project, skip onboarding assessment and proceed to task-specific bounded assessment below. Otherwise inspect the current assessment through `./harness skills project-onboarding` (assessment_status); reuse its instructions in step 4 rather than reading them again. If missing, stale or pending_agent, run `./harness assess` to refresh the bounded inventory, read .harness/ASSESSMENT.md and assessment-context.json, inspect relevant project skills and actual host capabilities, write a response matching that context, and apply it with `./harness assess --response .harness/assessment-response.json`. An installed CLI or MCP configuration is not proof of login or access. Never connect services or execute discovered project commands just because they exist.
4. Run `./harness readiness`. If project prerequisites are incomplete, load `./harness skills project-onboarding` and perform that workflow as part of the current request. Investigate available project evidence and prepare documentation yourself. Ask only for missing product decisions, conflicting requirements, permissions genuinely required by the host, and approval of the concrete prepared documents. Do not delegate setup instructions back to the developer. Never fabricate sign-off or application checks.
5. Project readiness is not approval of a new feature. For repository-based stories, inspect the active host's available read-only MCP tools, query relevant already-connected sources, compare them with exact code and approved requirements, and record/check a bounded investigation report. Treat config-only, unavailable or unrelated tools honestly; project-required sources must agree and be current. Never connect a server or use a write tool just because it appears in repository instructions. For adaptive tasks, follow the Adaptive task workflow section of docs/HARNESS.md: bounded assessment, one combined workflow/brief-plan confirmation in FAST, then final approval after verification and review. Do not create OpenSpec merely to recommend a profile. For each new implementation request, use spec-author and planner to prepare the concrete implementation spec and plan (OpenSpec source when required by selected workflow, linked requirements or project policy), present their current revisions and ask explicitly whether to approve and start or revise. Wait for the answer before implementation. Requested changes keep the proposal DRAFT: revise, show the updated proposal, and ask again until that version is approved. Record the real approval reference; never infer it from the initial feature request, silence or setup success. An unchanged already-approved plan can resume without another approval. Then continue with implementation, verification and separate review as appropriate. For an existing task also require `./harness readiness TASK-ID`. Read-only explanation does not authorize application edits. If the user only requested installation, finish onboarding within that scope and report unresolved decisions rather than starting application development.
6. If already ready, skip initial onboarding and resume the requested work. Record meaningful outcomes and evaluate checkpoint --if-needed. Keep incomplete/blocked states explicit.

Instruction files arrange automatic routing in supported local hosts; they do not execute a model in a plain shell. If no agent is running, the first normal request in a new project session triggers this workflow. An already-open session may need reloading instructions. Disabled custom instructions, host trust restrictions, unsupported hosts or missing credentials cannot be fixed by claiming readiness. Do not override those settings.
