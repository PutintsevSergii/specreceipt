# Historical Harness v0.2.0 usage and contract

This document describes the earlier `my-ai-harness@0.2.0` package. For current commands and upgrade behavior, read [SpecReceipt v0.3.0](V03.md).

This private package is unpublished. Use a local archive; no public-registry availability is claimed. Node >=20.19 and <25, Python >=3.11, and POSIX are required for execution. macOS and Linux/WSL are supported designs; local release evidence covers macOS ARM64 only. Native Windows engine execution is refused. Git is required for divergent text merges.

## Installation and unified CLI

```sh
npm install --ignore-scripts --no-audit --no-fund /absolute/path/my-ai-harness-0.2.0.tgz
./node_modules/.bin/my-ai-harness init --target /absolute/project --yes
./node_modules/.bin/my-ai-harness doctor --target /absolute/project --json
```

Install the pinned official OpenSpec 1.14.3 locally before init: `npm install --prefix /absolute/project/.harness/tools/openspec @fission-ai/openspec@1.14.3`. Init stages its actual Codex generation; it never overwrites existing OpenSpec customization. Navigation dependencies are provisioned explicitly through `my-ai-harness tools update --apply --only codegraph graphify`. Dependencies require their supported runtimes and network or a populated local cache. Doctor does not install or upgrade anything.

Adaptive execution uses the existing initialization contract:

```sh
my-ai-harness init --target /absolute/project --agent codex --workflow openspec --quality strict --skills engineering-pack --yes
my-ai-harness workflow assess TASK-ID --facts .harness/task-facts.json --target /absolute/project
# Only after the developer explicitly approves the displayed workflow and plan:
my-ai-harness workflow confirm TASK-ID --profile FAST --by NAME --reference docs/approvals/task-plan.md --target /absolute/project
```

Use `copilot`, `copilot-ide` or a supported combined agent selection for the same Python-owned policy. `--workflow openspec` selects a specification integration, while `--quality strict` installs an engineering baseline; neither forces an adaptive task to STRICT. There is no `--workflow adaptive` init option. Prepare the task and actual facts before assessment; FAST in the example is a developer-selected outcome, not a preset recommendation. FAST/STANDARD need a task OpenSpec change only when linked requirements or project policy mandate it. STRICT retains its OpenSpec requirement and all existing gates. Initialization still provisions OpenSpec integration scaffolding; it does not create a task change or approve implementation. Final developer approval remains separate after VERIFIED and substantive review.

After installation, use `my-ai-harness COMMAND --target DIR`. Lifecycle arguments are parsed by the installed Python engine, including per-command `--help`. `--json` returns the protocol envelope; default output is the existing structured domain result or help text. Missing target defaults to cwd.

| Operation | Behavior |
| --- | --- |
| `task start ID`, `task transition ID STATUS --reason TEXT` | Existing readiness, scope and evidence gates |
| `task approve ID --kind KIND --by NAME --reference FILE` | Existing bound approval validation; no synthesized approval |
| `review ID --by NAME --reference FILE` | Python-owned alias of task approve with kind review; requires the existing structured review document |
| `run --max-steps N --max-seconds N` | Existing bounded opt-in adapter runner; no implicit agent configuration |
| `verify ID`, `regression ID` | Execute configured checks and persist evidence |
| `status`, `resume`, `next`, `readiness [ID]` | Existing reconciliation and readiness semantics |
| `onboarding`, `skills`, `openspec`, `indexes`, `graph`, `graphify`, `codegraph`, `tools` | Existing subcommands and parameters |
| `validate`, `self-test`, `checkpoint`, `note`, `recovery`, `engineering-log`, `adopt` | Legacy operations through the same engine |
| `init`, `doctor`, `upgrade` | Distribution operations; doctor is read-only |

Legacy `python3 -B harness ...` and `./harness ...` remain compatible. npm users should prefer the unified executable. `review` records a supplied review, it does not launch a reviewer. `run` does not grant permission or invent a model adapter.

## Engine boundary

Package version, engine implementation version and protocol version are independent fields. This release pairs package 0.2.0 with engine 0.2.0, protocol 1 and product config schema 2; lifecycle schemas remain unchanged. The adapter rejects mismatches with an upgrade diagnostic. No initialized project silently falls back to the bundled engine. Doctor and lifecycle execution verify the same installed engine inventory and hashes before loading it in isolated Python mode. A customized engine must be maintained as an explicitly versioned fork; upstream upgrade refuses to relabel it.

One stdin JSON request: `{ "protocolVersion": 1, "target": "/absolute/project", "argv": ["status"] }`. The working directory must equal target; `--root` overrides are forbidden. One stdout JSON response contains `protocolVersion`, `engineVersion`, `target`, `cwd`, `engineRoot`, `operations`, `exitCode`, `data`, `error`. `contract` negotiates metadata and operations derived from Python argparse. Human diagnostics go to stderr. The OS exit code matches exitCode: 0 success/help, 1 operation failure/block, 2 invalid request/arguments. Invalid requests may omit target/operation metadata. The adapter checks status and identity, never parses console prose for success.

Python initialization runs against staged installation inputs and supplies the initial state and setup journal. TypeScript only provisions those bytes through its recoverable transaction. Existing project state/history is preserved. Python processes have bounded output and a 30-minute timeout; interruption is an error and uncertain domain operations require inspection/resume, never blind replay. Timeout is an adapter ceiling, not a guarantee that arbitrary grandchildren or external side effects have stopped; inspect running adapters before recovery.

## Upgrade and recovery

Install the new local archive into a separate tooling consumer, then invoke that consumer's executable against the project. This selects the new package without publication or executing package scripts.

```sh
# A baseline is the extracted or npm-installed old package directory containing package.json.
/path/new-consumer/node_modules/.bin/my-ai-harness upgrade --target /project --baseline /path/old-consumer/node_modules/my-ai-harness --dry-run
/path/new-consumer/node_modules/.bin/my-ai-harness upgrade --target /project --baseline /path/old-consumer/node_modules/my-ai-harness
/path/new-consumer/node_modules/.bin/my-ai-harness doctor --target /project --json
```

Manifest schema 2 records package/engine/protocol/config versions, applied migrations, managed file hashes, original template bytes/hashes and Skill source identities. A file's installed checksum can differ from its upstream baseline after a successful merge. For v0.1.0, unchanged local content is hash-verified as a baseline; edited content requires a matching archived template. Never execute old package code to reconstruct it. Unknown baselines fail explicitly.

Git merge-file combines BASE original, LOCAL user file and REMOTE new template. Only the managed AGENTS section is merged; surrounding rules survive. Custom Skills, project docs and OpenSpec-owned files survive. Overlap, local deletion, unowned collision and removed/renamed ownership paths produce explicit conflicts with no target writes. This release deliberately requires manual ownership migration for removals/renames; automatic rename inference is unsupported. Preserve backups and reconcile paths/baselines deliberately rather than editing hashes to conceal a conflict.

Product config migration 1→2 validates input, preserves supported selections and adds `engine.protocolVersion: 1`. It validates the result and records `product-1-to-2` once. Unknown fields/versions fail closed. Lifecycle state is not migrated by TypeScript.

Upgrade prepares the full write set, stages engine negotiation, records prior bytes/modes and expected outputs in `.harness/installation-pending.json`, applies only unchanged preimages, then validates with the installed engine before deleting the journal. A failure retains backup/intent. Inspect it, ensure no writer is running, then run `my-ai-harness upgrade --target /project --recover`. Concurrent edits block recovery rather than being discarded. A killed process can leave `.harness/installation.lock`; confirm it is stale before removing it manually. Empty directories may remain after rollback. No third-party command runs as an upgrade migration and external effects are not represented as transactional.

Quiesce legacy v0.1.0 writers before upgrading: that engine predates the shared installer lock. v0.2.0 lifecycle mutations and installer transactions share the exclusive lock. These are cooperative locks, not protection against hostile writers or agent edits.

## Troubleshooting and quality

Missing Python: install >=3.11 or set HARNESS_PYTHON to a compatible interpreter. Invalid engine/protocol: use matching package/upgrade, restore damaged engine bytes; do not use doctor as an upgrade. Missing baseline: supply the original package of the recorded version or resolve manually. An invalid config is not overwritten. Missing indexes continue blocking application work. Installation HEALTHY does not approve onboarding, requirements, checks or task completion. Required verification, review, explicit approvals and current evidence remain necessary. Local editable metadata is not authenticated authorization or protected CI.

## Release procedure

From source: `npm run check`, `npm run build`, `npm test`, `./harness validate`, `./harness self-test`. Set HARNESS_REAL_OPENSPEC to the real pinned executable to include its integration test. `npm run test:package` verifies isolated packed installation. `npm run test:upgrade` uses actual archives in release/ and independent npm consumers; set HARNESS_TEST_NPM_CACHE to a populated cache for offline installs. Fixtures using tool doubles are explicitly identified in their tests.

`npm run test:e2e` is opt-in real Codex execution, not part of ordinary tests. It installs the packed archive outside source, runs doctor, records versions, checks existing authentication, then invokes Codex with `--json --sandbox workspace-write --ignore-user-config --ephemeral`. It never disables security protections or changes personal config. Generated spec/plan approval remains a real operator step; without it the scenario is PARTIAL/BLOCKED. Preserve the report's disposable directory for inspection and continuation; no automatic rerun invents approval. Inspect emitted commands, skill reads, OpenSpec artifacts, source/test changes, independent assertions, task/evidence/review and DELIVERY.md. A final agent message cannot establish PASS.

Official invocation reference checked for this release: [Codex non-interactive mode](https://learn.chatgpt.com/docs/non-interactive-mode). Installed `codex exec --help` is recorded alongside the trace. Complete success requires all release acceptance criteria; live authentication alone is insufficient.

To continue the same disposable scenario after actual operator approval, preserve the original directory and record the actual approved scope and document revisions in its `docs/approvals/operator.md`. Set `HARNESS_E2E_CONTINUE` to the report's `base` directory and rerun `npm run test:e2e`; prior traces are retained. Continuation does not manufacture approval or reinitialize the target. Reinstall/upgrade the consumer explicitly first if testing a newer archive. Approval provenance still requires operator review; the script cannot authenticate a Markdown assertion.
